# AGENTS.md — parking-system

This folder is a Flywheel **Local** site directory containing **two related but separate applications**:

1. `app/public/` — a WordPress site: the **legacy** Thai parking-booking / car-rental system (custom theme `fluffy-dev`, WooCommerce, 2C2P payments, LINE OA notifications).
2. `parking-platform/` — the **standalone rewrite** of that system: Next.js 15 + Go (Fiber) + PostgreSQL, with a `cmd/migrate-wp` tool intended to import data from the WordPress MySQL database.

Neither is a git repository. There is no CI, no lint config beyond defaults, and no test suite anywhere. Do not invent conventions that don't exist; follow the patterns already in each codebase.

## Directory map

```
parking-system/                  # Flywheel Local site (do not restructure)
├── app/
│   ├── .envrc                   # auto-generated by Local: PHP/MySQL/wp-cli/composer on PATH (direnv)
```

# Part 1 — WordPress site (`app/public`)

## Environment facts

- Runtime: PHP **8.2.29**, MySQL **8.4.0** (bundled by Local, see `app/.envrc`). WP-CLI and Composer are bundled with Local; use direnv (`app/.envrc`) or Local's shell for correct `PHPRC`/`MYSQL_HOME`.
- Site URL is stored **in the DB** (no `WP_HOME`/`WP_SITEURL` constants); default Local URL `http://parking-system.local`.
- `wp-config.php`: `WP_ENVIRONMENT_TYPE=local`, `WP_DEBUG` guarded and false by default. **PHP-level `display_errors` is On** and `error_log` points to `logs/php/error.log` (from `conf/php/php.ini.hbs`) — that's where errors actually appear, not `wp-content/debug.log`.
- Mail is captured by **Mailpit** (`logs/mailpit/`, php.ini `sendmail_path`) — no real email is sent locally.
- **`DB_CHARSET` is legacy `utf8`, not `utf8mb4`** — beware with emoji/rare Thai characters.

## Theme: `fluffy-dev`

Standalone Underscores-based commercial theme ("Fluffy" by Vecular/YourPlans, text domain `fluffy`). Not a child of twenty*. `composer.json` is an `_s` leftover. It ships an **EDD theme updater pointed at vecular.co** — an in-dashboard "theme update" can overwrite customizations; never trigger it.

### Two-generation architecture (most important convention)

Every major feature exists **twice**:

- **Legacy jQuery**: flat page templates (`login.php`, `register.php`, `checkout.php`, `checkin.php`, `page-carpark.php`, `page-rentcar.php`, `profile-page.php`, `service-control.php`, `create-driver-job.php`, `page-dashboard.php`, …) + scripts in `customize/js/ajax-*.js` and `booking/` (flatpickr with Thai locale, Swiper, select2, `tabien-popup.js`, `space-parking.js`).
- **Current React**: sources in `src/react/{auth,profile,booking,operations,dashboard,admin,shared,styles}`, built with `@wordpress/scripts` into **`build/react/` (committed — a generated artifact, never hand-edit; source of truth is `src/react/`)**.
  - Build commands (from theme root, which has `package.json` + `package-lock.json`):
    ```powershell
    npm install        # node_modules may already exist
    npm run build      # emit build/react/{auth,profile,booking,operations,dashboard,admin}.{js,css,.asset.php}
    npm run start      # watch mode
    npm run lint:js    # wp-scripts lint on src/react only
    ```
  - `inc/react-app.php` is the wiring hub: maps each page template (or page slug fallback like `carpark`, `profile`) to one bundle, enqueues it, and injects `window.fluffyReactConfig` (ajaxUrl, REST base `custom/v1`, per-feature nonces, user/driver info, `lang` th/en). Page templates are thin mount points: `<div id="fluffy-booking-root" class="fluffy-react-root" data-mode="carpark">` etc.; `data-mode` selects the sub-app.
  - `fluffy_dequeue_legacy_scripts_for_react()` strips old jQuery scripts on React pages (hooks at priority 99). **Check `inc/react-app.php` before touching either side of a feature.**
  - Shared helpers: `src/react/shared/api.js` (wpAjax/wpRest) and `src/react/shared/i18n.js` (`t(th, en)`).
- Admin-side React: `inc/admin-react-app.php` adds the **"Parking System"** WP admin menu hosting `build/react/admin.js` (REST `custom/v1/admin/*`, `manage_options` only). It includes an Elementor page cleanup tool guarded by an allowlist of protected booking templates (`fluffy_get_protected_booking_templates()`).

### Styling

No SCSS, no CSS bundler. Plain committed CSS (`css/`, `customize/css/`) plus **DaisyUI 5 from CDN and `js/tailwind-4.js` (Tailwind v4 *browser* build)** enqueued on every page — class changes need no build step, and some flows dequeue the theme's own `fluffy-style` (see `customize/customize.php`).

### Where the logic lives

- `functions.php` (~2200 lines): enqueues, ACF options pages ("Site Settings" slug `vc-site-settings`, Footer/Social sub-pages), cron schedules (`every_30_minutes` → `parking_reminder_event`), big hardcoded HTML "OK Parking" email templates, WooCommerce coupon metabox (`_product_coupon`), admin columns.
- `customize/customize.php` (~3000 lines): REST route registration, WooCommerce order creation for parking bookings, script enqueues. It requires `inc/multilingual-functions.php` and `customize/control/*.php` AJAX handlers (signin, signup, ajax-forgotpassword, carrent, customer-profile, add-driver-job, service-management).
- `dashboard/{parking,carrental,driver,transport}-management/*.php`: admin management REST endpoints.
- REST namespaces: `custom/v1` is the main one; also `taxi/v1`, `parking/v1`, `carrental/v1`, `profile/v1`, `carrent/`, `mytheme/v1/settings` — registration is scattered across the files above.
- `check-fight.php` is **not required** (commented out in `customize.php`); the aviationstack flight-lookup script (`customize/js/aviationstack/flight-lookup.js`, hardcoded API key) is registered but inert unless the require is re-enabled.

### Data model (mostly lives in the DB, not in code)

- **Custom post types are registered with Custom Post Type UI in the database**, not in code: `parking_booking`, `car_rentals`, `package_rent`, `taxi-driver`, `ride_assignment`, `parking_space`, `tabien-rod`, plus `booking_status` taxonomy (term-level ACF `color` field). You will not find `register_post_type` for these by grepping.
- **ACF PRO fields are DB-only**: no `acf-json/` folder, no `acf_add_local_field_group()`. The theme-root `acf-export.json` is a stale 2-group reference export. Changing a field means changing it in the admin UI (Local MySQL), and the change is invisible to file-based review.
- Payments run through **WooCommerce**: bookings create WC orders (`customize/customize.php` for parking, `customize/control/carrent.php` for rentals); status flows `woocommerce_order_status_processing` → update ACF booking status, `woocommerce_payment_complete` → email, `woocommerce_thankyou` → redirect `/thank/`. The 2C2P gateway adds custom status `wc-awaiting-payment`. Theme overrides WC templates in `woocommerce/checkout/`.

### i18n / Thai convention (not gettext)

Site default is Thai; Polylang Pro handles *content*. **UI strings use dual-text helpers, not `__()`**: `yp_text($th,$en)` / `yp_text_get()` (`inc/multilingual-functions.php`), `parking_text($key,$th,$en)` plus a localized `parkingTranslations` JS object (`js/parking-translations.js`, `wp_localize_script('wpt-script', …)`). Don't "fix" these into gettext. Escaping is inconsistent between old files (`functions.php`, `customize.php` echo raw ACF values) and newer ones (`inc/react-app.php`, `header.php`, `inc/admin-react-app.php` use `declare(strict_types=1)` + `esc_*` + REST nonces) — **new code follows the newer style**.

### Custom-authored plugins (in `wp-content/plugins`)

- `yp-qrcode/` — shortcode `[yp_code]` generating QR PNGs via bundled phpassqrcode into `wp-content/plugins/yp-qrcode/qrcodes/`. **Cached forever**: existing files are not regenerated. Theme check-in/out relies on an ACF `qr_code_url` field. Vendored `vendor/` — don't edit.
- `2c2p-yourplans-2025/` — 2C2P WooCommerce redirect gateway (v8.5 API), writes ~30 `wc_2c2p_*` order meta keys; registers `wc-awaiting-payment`. Booking-status side effects live in the **theme**, not here.
- `designil-pdpa/` — Thai PDPA cookie consent (by Your-Plans). **Gotchas**: `yp-path.php` auto-flags the license option as valid on init; it *regenerates* per-language minified JS/CSS into `wp-content/designil-pdpa/` from admin settings — those files are generated, never hand-edit.
- `vc-prompt-font/` — enqueues licensed Thai Prompt `@font-face` (copyright font, don't redistribute).
- `wpt-chat-button/` — floating contact buttons driven by `vc_floating_icon_*` options.
- `ds-all-device-css/` — admin CodeMirror page storing per-breakpoint CSS in DB options, echoed as raw `<style>` in `wp_head`. **Site-wide CSS overrides can hide in the database**, not theme files.
- `wpt-admin-menu-restrictions-ui/` — per-role admin menu hiding/renaming + direct-URL blocking (`wpt_amr_roles`). Admin screens can "disappear" per role because of this.

### mu-plugins

Only two SecuPress Pro drop-ins that define `COOKIEHASH` and derive the auth salts at runtime (pluggable `wp_salt()`). **Deleting them or rotating SecuPress salts logs everyone out.**

### Caching

**Breeze** page cache is live: `wp-content/advanced-cache.php` drop-in + `wp-content/breeze-config/` + `wp-content/cache/breeze-minification/`. Purge Breeze after template/CSS changes or you'll test stale HTML. (A WP Rocket lazyload filter exists in code though WP Rocket isn't installed — legacy remnant.)

# Part 2 — `parking-platform/` (new app)

## Stack & commands

- Backend: Go **1.23**, Fiber v2, pgx/v5, sqlc, robfig/cron v3, golang-jwt/v5, bcrypt. Module name `parking-platform/backend`.
- Frontend: Next.js **15** (App Router, Turbopack dev), React 19, TypeScript strict, Tailwind **v4** (CSS-first: `@import "tailwindcss"` in `globals.css`, no `tailwind.config.ts`), TanStack Query / zod / lucide-react installed but not yet used. Path alias `@/* → src/*`.
- Infra: Docker Compose (`postgres:16-alpine`, `redis:7-alpine`, built Go API) — see `docker-compose.yml`. TZ `Asia/Bangkok` throughout.

```powershell
# from parking-platform/
Copy-Item .env.example .env
docker compose up -d --build          # postgres + redis + API on host :8080

cd frontend; npm install; npm run dev # Next.js on :3000
npm run typecheck                     # tsc --noEmit (the real validation command, no tests exist)
npm run build; npm run lint           # lint script exists but no eslint config is present

# sqlc codegen (run from parking-platform/):
docker run --rm -v "${PWD}/backend:/src" -w /src sqlc/sqlc generate
# (or local `sqlc` binary from backend/)

# Backend without Docker:
cd backend; go run ./cmd/api          # needs DATABASE_URL etc. exported — no dotenv loader in Go code
go build ./... ; go vet ./...         # backend validation commands
```

## API conventions

- All routes under `/api/v1` (+ `GET /health`). Route groups: `/auth`, `/parking`, `/ops`, `/car-rentals`, `/coupons`, `/checkout/2c2p`, `/webhooks/2c2p`, `/vehicles`, `/dashboard`.
- Response shapes (set by the existing code): success `{"success": true, "data": ...}`; 500 `{"error": "..."}`; unimplemented 501 `{"success": false, "error": {"code": "NOT_IMPLEMENTED", "message": "Endpoint scaffold ready: <action>"}}`.
- Frontend calls the API directly (no Next.js proxy/rewrites); CORS allows only `APP_BASE_URL` with credentials, so change `APP_BASE_URL` if the frontend origin moves.

## Critical gotchas

1. **This is a deliberate scaffold, not finished work.** ~34 of 35 handlers are `s.notImplemented(action)` stubs; the only real handler is `listLocations` (and it uses **raw `s.Pool.Query()` SQL, not sqlc**). The intended work is implementing stubs — decide explicitly whether to use the ready `sqlcgen` Querier (`sqlcgen.New(pool)`, `WithTx`) or inline pgx SQL, and keep the response shape above.
2. **Migrations**: no migrate tool is wired. Postgres applies only `000001_init_schema.up.sql` via a `docker-entrypoint-initdb.d` bind mount **on a fresh volume**. Consequences: later migration files won't auto-apply; to re-seed you must `docker compose down -v` (drops `postgres_data`); the up file must stay valid to run standalone.
3. **Config**: env-only (`internal/config` with hardcoded dev defaults). Docker injects `DATABASE_URL` with host `postgres`, which doesn't resolve outside the compose network — use `localhost:5432` when running `go run` on the host.
4. **sqlc overrides**: `uuid → string`, `timestamptz → time.Time` — IDs are Go strings everywhere (raw SQL casts use `id::text`).
5. **Auth is designed but not enforced**: JWT package + `refresh_tokens` table + `users.password_algo` (`'wp_phpass'` | `'bcrypt'`) for legacy WP password migration with `needsRehash`. No Fiber JWT middleware is registered yet. Preserve the phpass compatibility.
6. **Provisioned but unused**: Redis (loaded into config, no client), `internal/db/sqlcgen`, `internal/auth`, `src/lib/api.ts` (never imported). Don't assume they're wired.
7. **Fake pieces to know about**: 2C2P `CreatePaymentToken` returns a signed payload without calling the gateway; LINE cron jobs log only; `cmd/migrate-wp` is a stub.
8. **Never hand-edit**: `backend/internal/db/sqlcgen/`, `frontend/next-env.d.ts`, `frontend/tsconfig.tsbuildinfo`, `frontend/.next/`, `node_modules/`, theme `build/react/`, `wp-content/designil-pdpa/`, vendored plugin dirs.
9. **Locale/brand**: UI copy is Thai (`lang="th"`), TZ `Asia/Bangkok`, brand color `#29b2e2`, API/DB JSON in snake_case.

## WordPress ⇄ platform relationship

- `parking-platform` replaces `fluffy-dev` features one-to-one (the homepage cards in `frontend/src/app/page.tsx` name the WP files they replace; cron jobs mirror WP `every_30_minutes` reminders).
- Data migration path: `cmd/migrate-wp` reads the **Local MySQL** DB of the WP site (`WP_MYSQL_DSN=root:root@tcp(127.0.0.1:10005)/local`, prefix `wp_` from `.env.example`) into Postgres; the PG schema deliberately keeps `wp_user_id`/`wp_post_id` columns and `wp_phpass` password support.
- When changing behavior on one side, check whether parity on the other side matters before assuming you can change one alone.
